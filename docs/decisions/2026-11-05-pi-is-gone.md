# Pi is gone — the runner runs on Mastra alone

## Context

[2026-11-05-the-run-runs-on-mastra](2026-11-05-the-run-runs-on-mastra.md) put the Mastra
engine **beside** Pi: `--engine pi|mastra` chose, Pi was the default, and the Pi session
was to stay "until the last Pi session is gone". Two engines, one runner.

Pi did not leave. Three packages still carried it:

- `@quintinshaw/pi-dynamic-workflows` — the **graph** that moved a session through its
  states. It was written for Pi and pulls Pi's SDK in with it: its `dist/agent.js`
  imports `@earendil-works/pi-coding-agent`, and it declares it as a peer dependency. So
  the graph was a Pi engine wearing another name, and "Pi is behind a flag" was true of
  the session and false of the tree.
- `@gotgenes/pi-permission-system` — the **guard**, the Pi extension that gated every
  tool call and read its policy from a file in the worktree.
- `@earendil-works/pi-coding-agent` — the **SDK** itself, a peer dependency, with the
  version gate (`src/version.ts`) that refused to run against a Pi outside the pinned
  range, and the package's entire public API (`src/index.ts` exported
  `assertInstalledPiVersion` and nothing else).

Two engines also mean two copies of every rule. The guard's policy had to be read by
both carriers so they could not refuse different things; the tools had to be described
once and built twice (`src/pi-tools.ts` and `src/mastra/tools.ts`); the journal had to
be written twice so the two engines spelled a line the same way. Every one of those
copies is a place the two can drift.

And the graph does not want an engine. The runner's rules — the deadline, the stop, the
cut-off, the decision nodes, the review loop that retries until the verdict passes — are
the runner's own, and they were written as three scripts fed to a workflow engine that
was built for something else.

## Idea

Take Pi out of the runner completely: the SDK, the workflow engine, the permission
system, the version gate and the package's public API all go. Mastra is the only engine.
The graph is the runner's own TypeScript.

## Decision

**Pi is out.** `@earendil-works/pi-coding-agent`, `@quintinshaw/pi-dynamic-workflows`
and `@gotgenes/pi-permission-system` leave the dependencies; `src/pi-tools.ts`,
`src/version.ts` and `src/index.ts` leave the tree. Nothing in a run imports the Pi SDK,
directly or through a peer dependency.

**The `--engine` flag is gone.** There is one engine. `--engine pi` and `--engine
mastra` are usage errors, and `--agent-dir` — Pi's agent directory — with them.

**The graph is the runner's own code.** `src/workflow.ts` is a TypeScript graph: the
states, the action nodes, the branch, the review loop, the cut-off and the failure.
`@quintinshaw/pi-dynamic-workflows` gave the runner three things — `phase()`, `agent()`
and `gate()` — and those three are now the runner's own words. The public API of
`src/workflow.ts` does not change: `WORKFLOW_STATES`, `WORKFLOW_ACTIONS`, `WorkflowState`,
`StateOutcome`, `TurnRunner`, `StatesResult`, `runStates`, `runWorkSession`,
`runReviewGate` and the errors keep their names and their shapes.

> graph has moved: it runs on Mastra's workflow engine, and it is a set of components in
> `src/workflow/` — the states, the tokens, the errors, the step, the straight line, the
> work session, the review loop. The rule now is in
> `2026-11-06-the-graph-runs-on-the-mastra-workflow-engine.md`: the engine carries the
> states, the branch and the loop, and the runner's own rules — the deadline, the stop,
> the cut-off — stay the runner's. The rest of this record stands.

**The guard is one policy and one carrier.** `GUARD_POLICY` (`src/guard.ts`) stays the
one list of rules; the carrier is Mastra's workspace hook `beforeToolCall`
(`src/mastra/guard.ts`). The Pi extension, the policy file it read from the worktree and
the git exclude that kept it out of the tree are gone.

**The version gate is gone.** It gated the Pi SDK, and there is no Pi SDK to gate. So is
the package's public API: a package whose only export was a version check is a command
with a public API it does not need. `package.json` has no `exports`, no `main` and no
`types` — it is a `bin`.

**The seams stay.** `AgentSession` and `SessionFactory` (`src/session.ts`) are still the
face of a session, and `TurnRunner` and `StatesResult` are still the face of the graph.
`src/runner.ts`, the record, the gates, the budget, the merge mode and the contract do
not learn what the engine is.

**A broken review is fatal.** The old engine's review failure was *recoverable* and was
swallowed; the review loop carried on. Under the runner's own graph a review that fails
is a failed turn, and a failed turn stops the run: the finding stays on the issue and
the next run continues it. The cut-off, the "fix changed nothing" and the "review stated
no verdict" outcomes keep their own, separate ways out — those are decisions, not
failures.

**The skills' carrier is the runner's own.** The runner reads its own `skills/` and the
target repository's `.agents/skills` (`src/mastra/skills.ts`) and hands the directories
to the agent. The target's own copy of a skill wins over the runner's, so a skill is
carried once. The target's `.pi/skills` is no longer read: Pi's directory is Pi's.

**The package is a command.** `npm run check` is the gate; there is nothing to import.

## Rationale

**Why not keep the flag.** Two engines is one too many for a runner with one job, and
the cost is not the flag — it is the copies. Every rule the two engines both applied
needed one carrier on each side, and each copy was a place the engines could drift. The
session was the only thing that needed to be swappable, and it has been swapped.

**Why the graph is not a Mastra workflow.** The rules the graph enforces are the
runner's own: a failed turn stops the run, a cut-off run comes back aborted with the
states that finished, the review loop retries until the verdict passes. A workflow
engine would have to be told all of that, and the runner's own rules would end up
spread across two layers: the runner's, and the engine's own statuses. Written directly,
the graph is about a hundred lines and the rules stay in one file. The engine was also
the thing that pulled Pi back in, so the choice was not only about taste.

**Why the version gate and the public API go with Pi.** The gate existed because a
runner written against an old SDK fails by doing the wrong thing rather than by
stopping. There is no SDK to be old against: `@mastra/core` is pinned exactly, at
1.81.0, in `package.json`. And a package that exports only a version check is a
library in name; the runner is a command, and a command that exports nothing cannot
break its callers.

**Why a broken review is fatal now.** The old behaviour was the engine's, not the
runner's: a recoverable failure was swallowed and the loop carried on, which turned a
broken review into a run that looked finished. The runner's own rules already say that
a failed turn stops the run; the graph now agrees with them.

**Why this supersedes the two records above.** The Mastra record decided that the graph
would be a Mastra workflow and that the engines would sit side by side until a switch —
both are decided otherwise here, and the parts that stand (the seams, the skills rule,
the guard rules, the model as a gateway) are restated above. The command record decided
that the version gate moves into the session factory and that the package exports it;
with no Pi SDK there is nothing to gate, so that part goes, while the record's own
decision — the runner is a command, not an extension — stands.

## Consequences

- Dependencies: `@mastra/core` (1.81.0, pinned), `@mastra/memory`, `@mastra/schema-compat`,
  `@ai-sdk/anthropic`, `typebox`, `undici` and `chalk` stay; the three Pi packages go.
  The `peerDependencies` section goes with them.
- Files: `src/pi-tools.ts`, `src/version.ts`, `src/index.ts`, `.pi/settings.json`,
  `test/package.test.ts` and `test/cli.test.ts` are deleted. `src/workflow.ts` (now
  `src/workflow/`), `src/guard.ts`, `src/cli.ts`, `src/session.ts` and `src/mastra/skills.ts`
  are rewritten or narrowed; `src/mastra/*` is the whole engine now.
- The journal is written once: `src/journal.ts` and `src/mastra/log.ts` are the only
  writers, and there is one spelling of a line.
- The guard's policy file — a repository's committed Pi policy — no longer governs a
  run, and the runner's own deny list does.
- A worktree no longer carries a `.pi/` directory: nothing writes it and nothing reads
  it.
- The package is a `bin` with no exports. A caller that embedded the runner to call
  `assertInstalledPiVersion` has nothing to call.
- The memory of a run still lives in the process (`InMemoryStore`): a run that restarts
  loses its context. That is no worse than it was, and the README does not promise
  memory.
- `spike/` — the record of what Pi's packages did — goes with Pi. Its findings live in
  this record now.
